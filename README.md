# RailETA — Real-Time Indian Railways Train ETA Prediction System

## 1. Project Overview
**RailETA** is a production-ready, persistent full-stack web application and machine learning pipeline designed to predict and display dynamic train arrival times (ETAs), P10–P90 prediction intervals, and confidence scores across railway corridors. It combines live train state (position, speed, running delay), route schedules, historical section running times, weather conditions, and track congestion with a tree-based quantile regression ensemble (`HistGradientBoostingRegressor`).

It includes a multi-device **Persistent Data Center** (`/data`), **Manual Telemetry & CSV Playback Control** (`/demo-control`), **Application Authentication** (`/login`), and a **Real Geographic OpenStreetMap Live Tracker** (`/status/:trainNumber`).

## 2. Honest Simulated/Synthetic Data Disclaimer
> **Important Notice (`SIMULATED_DEMO_DATA (seed=42)`)**:
> This application operates on **Synthetic Demo Data (`SIMULATED_DEMO_DATA (seed=42)`)** and **Prototype Telemetry** generated by a deterministic railway kinematics & delay-propagation generator (`backend/app/services/data_generator.py`), user-uploaded CSV datasets (`backend/app/services/dataset_service.py`), or manual telemetry overrides (`backend/app/routes/telemetry.py`).
> - Unless an external railway API is explicitly configured via `RAILWAY_API_URL` and `RAILWAY_API_KEY`, RailETA does **not** claim to receive an official live GPS feed from Indian Railways / CRIS NTES.
> - All reported ML evaluation metrics (MAE, RMSE, Median AE, P90 AE) are evaluated on a chronological time-based split of the deterministic synthetic dataset or user-uploaded historical runs and must **not** be presented as official Indian Railways operational statistics.

## 3. System Architecture
RailETA enforces a modular provider architecture so the demo telemetry simulator, manual telemetry controller, uploaded CSV telemetry player, and external railway API feed share the exact same downstream ML and WebSocket pipeline:

```text
TelemetryProvider (Simulator | Manual | Uploaded CSV | External Railway API)
  → Coordinate & Route Interpolation (backend/app/services/telemetry_providers.py)
  → Feature Engineering (backend/app/ml/feature_engineering.py)
  → HistGradientBoosting Quantile Ensemble (backend/app/ml/prediction_service.py)
  → Persistent ETA & State Service (backend/app/services/eta_service.py)
  → Cloud PostgreSQL Persistence (backend/app/database.py & backend/app/models/railway.py)
  → REST API & WebSocket Broadcast (backend/app/routes/ & backend/app/websocket/)
  → React + OpenStreetMap Leaflet + Recharts Frontend (frontend/src/)
```

## 4. Persistent PostgreSQL Architecture
All application state is stored in a shared relational database (`DATABASE_URL` pointing to hosted PostgreSQL on Render / Neon / Supabase, with automatic local SQLite fallback `sqlite:///./raileta_v3.db` when `DATABASE_URL` is unset):
- **`users`**: Application accounts with `bcrypt`-hashed passwords (`password_hash`). Plaintext passwords are never stored or logged.
- **`datasets`**: Persistent catalog of seeded and user-uploaded datasets, validation summaries, row counts, and uploader metadata.
- **`trains`**, **`stations`**, **`routes`**: Core railway network entities and station geographic coordinates (`latitude`, `longitude`).
- **`train_positions`**: Latest live position, speed, delay, `data_source` (`SIMULATED_LIVE`, `MANUAL_TELEMETRY`, `UPLOADED_TELEMETRY`, `EXTERNAL_API`), and weather/congestion state.
- **`predictions`**: Station-wise ML predicted arrival times, P10–P90 bounds, and confidence scores.
- **`historical_runs`**: Section running times and historical arrival delays used for ML training and empirical delay aggregation.
- **`weather_records`** & **`telemetry_records`**: Persistent corridor weather observations and chronological GPS/speed/delay telemetry frames for live CSV playback.
- **`system_state`**: Shared key-value state storing active `data_mode` (`AUTOMATIC_SIMULATION`, `MANUAL_CONTROL`, `UPLOADED_TELEMETRY`) across all connected clients.

On startup (`initialize_system()` in `backend/app/main.py`), RailETA runs idempotent seeding (`seed_all_tables_if_empty`): if the PostgreSQL database already contains trains or uploaded datasets, existing data is preserved across restarts and redeployments.

## 6. How to Upload Data (`/data`)
1. Sign in at `/login` using the Demo Account (`demo` / `RailETA-Demo-2026`).
2. Navigate to **Data Center** (`/data`).
3. Select any of the 6 dataset categories:
   - **Historical Runs** (`historical_runs`)
   - **Train Data** (`trains`)
   - **Station Data** (`stations`)
   - **Route Data** (`routes`)
   - **Weather Data** (`weather`)
   - **Telemetry Data** (`telemetry`)
4. Click **Download Template CSV** to get a pre-formatted sample CSV (`Synthetic Demo Dataset`), or choose your own `.csv` file and click **Upload & Validate CSV**.
5. The backend validates required columns, missing value percentage, duplicate rows, coordinate bounds, and date ranges inside a database transaction (`POST /api/datasets/upload`), then commits the records to PostgreSQL.
6. Click **`[ RETRAIN MODEL ]`** (`POST /api/ml/retrain`) to explicitly retrain the `HistGradientBoostingRegressor` ensemble on the combined historical runs in PostgreSQL and view updated MAE / RMSE / Median AE / P90 AE metrics.

## 7. How Uploaded Data Persists Across Devices
Because uploaded CSV rows, dataset metadata, manual telemetry overrides, and retrained ML predictions are committed directly to the hosted PostgreSQL database (`DATABASE_URL`) rather than browser `localStorage`:
- Uploading a dataset or updating train telemetry on **Laptop A** writes to the shared cloud PostgreSQL instance.
- Opening the deployed Vercel URL on **Laptop B** (or an incognito window / mobile browser) and logging into `demo` / `RailETA-Demo-2026` queries the same FastAPI + PostgreSQL backend and displays the exact same uploaded datasets, row counts, telemetry state, and ML ETA predictions.

## 9. How Manual Telemetry Control Works (`/demo-control`)
- In **Manual Control** mode (`data_mode = MANUAL_CONTROL`), the background simulator pauses automatic overrides so manual inputs remain authoritative.
- Submitting the manual telemetry form (`POST /api/telemetry/update`) interpolates exact route coordinates between the selected current and next station (`interpolate_route_position`), updates `TrainPosition`, appends a `TelemetryRecord`, runs the 14-feature `HistGradientBoostingRegressor` pipeline (`force_ml=True`), commits updated `Prediction` rows to PostgreSQL, and broadcasts a `TELEMETRY_UPDATE` event over WebSocket (`/ws/trains/{train_id}`).

---

## 10. How CSV Telemetry Playback Works
1. Upload a `telemetry` CSV in `/data` (or use the pre-seeded telemetry records for `12951`).
2. In `/demo-control`, use the **CSV Telemetry Playback** panel (`POST /api/telemetry/playback`).
3. Choose a playback speed (`1x`, `2x`, `5x`, or `10x`) and click **Start Playback** (with **Pause**, **Resume**, and **Stop** controls).
4. Each chronological CSV row is stepped through the real ML ETA pipeline and broadcast live to all connected map and status views with the `UPLOADED TELEMETRY` badge.

## 11. ML Model and Evaluation Metrics
- **Model**: `scikit-learn` `HistGradientBoostingRegressor` ensemble (`squared_error` point estimator + $\alpha=0.10$ and $\alpha=0.90$ quantile regressors for P10/P90 uncertainty intervals).
- **14 Features**: `current_delay`, `current_speed`, `distance_to_next_station`, `distance_to_destination`, `historical_section_running_time`, `historical_average_delay`, `train_encoded`, `station_encoded`, `route_encoded`, `day_of_week`, `hour`, `weather`, `congestion`, `previous_station_delay`.
- **Chronological Split (`70% Train` / `15% Validation` / `15% Test`)**:

## 13. Render + PostgreSQL + Vercel Deployment Instructions

### Step 1: Provision Persistent PostgreSQL (Render / Neon / Supabase)
1. Create a managed PostgreSQL instance (e.g., via `render.yaml` `raileta-postgres` database or Neon/Supabase).
2. Copy the PostgreSQL connection string (`postgresql://user:password@host:5432/raileta_db`).

### Step 2: Deploy FastAPI Backend on Render
1. Connect repository to Render (`render.yaml` Blueprint or Web Service with Root Directory `backend`).
2. **Build Command**: `pip install -r requirements.txt && python -m app.ml.train_model`
3. **Start Command**: `uvicorn app.main:app --host 0.0.0.0 --port $PORT`
4. **Environment Variables**:
   - `DATABASE_URL`: Hosted PostgreSQL connection URL
   - `JWT_SECRET_KEY`: Strong random secret string
   - `DEMO_USERNAME`: `demo`
   - `DEMO_PASSWORD`: `RailETA-Demo-2026`
   - `CORS_ORIGINS`: `https://your-frontend.vercel.app,http://localhost:5173`
   - `MODEL_PATH`: `app/ml/artifacts/raileta_hgb_model.joblib`
   - `ENABLE_SIMULATOR`: `true`

### Step 3: Deploy React Frontend on Vercel
1. Import repository into Vercel with **Root Directory** set to `frontend`.
2. **Build Command**: `npm run build` | **Output Directory**: `dist`
3. **Environment Variable**: `VITE_API_URL=https://your-backend.onrender.com`
4. `frontend/vercel.json` handles SPA route rewrites for `/`, `/login`, `/data`, `/demo-control`, `/search`, `/status/:trainNumber`, `/details/:trainNumber`, `/analytics`, and `/about`.
